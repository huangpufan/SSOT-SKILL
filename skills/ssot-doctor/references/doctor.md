# Doctor Verification

Doctor verification checks whether existing SSOT content is still trustworthy. It does not catch up new commits/sessions; catching up new changes is the job of [`commit-audit.md`](../../ssot-audit/references/commit-audit.md) and [`conversation-audit.md`](../../ssot-audit/references/conversation-audit.md) respectively.

Use cases:

- Default companion step of proactive catch-up.
- CI pipeline or manual `ssot doctor` execution.
- About to declare Doctor `passed` / `no-op` / "no update needed".
- Need to verify whether `covered`, `converged`, or tracking-baseline claims have evidence support.

Doctor's `passed`, `no-op` or "no update needed" conclusions are stop conclusions and need an explicit scoped stop review. Reviewer choice follows [`status-protocol.md` §6](../../ssot-preflight/references/status-protocol.md#6-stop-review-gate): self-review is the default; independent review is required only for bootstrap overall `passed`, a `documentation_language` change, a `semantic_impact=high` protocol upgrade, or the first `coverage_result=converged` declaration.

Doctor verifies; it does not author new SSOT truth or catch up new commits and
sessions. Run deterministic lint before semantic review. For every
reader-facing body, use `reader-quality.md`: product and architecture take the
full task gate; other v2.60 covered scopes take the exact-scope gate. A clean
structural run cannot produce `no-more-required-changes` by itself.

When reviewing an apex move from `$ssot-closeout` or `$ssot-audit`, validate
the `stream_a` and `stream_b` anchors, confirm that they support the direction,
and require the rationale to explain why the opposite altitude is wrong.
Return `needs-fix` for any missing or unsupported part; Doctor does not write
the move.

## 1. Execution method

```text
1. Read SSOT/STATUS.md:
   - tracked_commit
   - tracked_session
   - tracked_skill_version
   - documentation_language
   - documentation_language_evidence
   - coverage states
   - open adjudications / open gaps / stop-review gate

2. Scan existing SSOT content per this file's checklist.
   - Finish L1 deterministic checks first.
   - Enter L2 semantic checks after L1 fully passes.

3. Output the stale list and recommended fix actions.

4. The agent may fix directly, or report to the user for decision.

5. If about to declare Doctor passed / no-op / "no update needed", record a scoped stop review; request an independent reviewer only when the claim hits one of the four status-protocol exceptions.
   - no-more-required-changes: may record Doctor pass in the STATUS.md stop-review gate.
   - needs-fix: apply remaining changes and re-run Doctor and the applicable stop review.
```

In standalone scenarios Doctor runs only verification checks; it does not run commit/session audits. In proactive catch-up Doctor usually runs after commit/session audits to verify the trustworthiness of existing SSOT against current state.

## 2. Checklist

The checklist has two layers. L1 deterministic checks can be executed quickly by the agent (results are pass/fail). L2 semantic checks need agent judgement. Doctor executes L1 first, then enters L2 after L1 fully passes. Neither layer changes the reviewer policy: use a scoped self-review by default and independent review only for the four exceptions in `status-protocol.md` §6.

### 2.1 L1 deterministic checks

L1 check criteria are structural: whether a field exists, whether a path is valid, whether a value is legal. Results are deterministic pass/fail.

The deterministic entrypoint is
[`assets/scripts/ssot-lint.sh`](../assets/scripts/ssot-lint.sh). Its stable
hard checks cover required STATUS/lifecycle fields, canonical paths and links,
source-lifecycle records, frontmatter/numbering, manifest/placeholder
completeness, open-risk ownership, research packets, and benchmark ownership.
Stable warnings cover heuristic density, readability, derived-index, shadow
ledger, and benchmark-ledger signals. `--strict` promotes warnings for CI.

At a `tracked_skill_version >= 2.59` tracking baseline, L1 additionally hard-fails
`[NARRATIVE-SUFFICIENCY]`, `[MANIFEST-COMPLETENESS]`,
`[SURFACE-COVERAGE]`, `[DIAGRAM-FIRST]`, and v2.59 authoring-meta leakage.
`[KISS-TABLE-DENSITY]` remains a warning because a human must decide whether a
dense reader-facing reference table still follows a self-contained explanation.
Protocol-owned `_manifest.md` machine registers are excluded; their shape and
coverage are governed by manifest-specific checks. The v2.59 extensions do not
retroactively hard-fail a `<2.59` consumer; focused
`--check-document-quality` intentionally previews the new gate during upgrade.

At a `tracked_skill_version >= 2.60` tracking baseline, L1 also hard-fails
`[READER-REVIEW-EVIDENCE]`, `[SURFACE-INVENTORY]`, and `[OWNER-INVENTORY]`.
These checks prove that the finite review inputs and durable artifact exist;
they do not decide whether the prose or evidence is true. A pre-v2.60 consumer
keeps its historical review interpretation until protocol-upgrade review
advances the tracking baseline.

Semantic truth still requires Doctor judgement: whether the prose teaches the
right mental model, current claim evidence is sufficient, product and
architecture boundaries are honest, decomposition follows runtime ownership,
and the reviewer selected under `status-protocol.md` §6 can teach the material
back against the reader-quality rubric. Lint narrows that review; it cannot
produce the comprehension verdict.

**v2.15 notes / v2.18 extended / v2.19 extended**: Reader Map, Readable Authority, generic diagram-candidate governance, evidence-guided decomposition, bottom-up synthesis, owner anchor, product owner boundary, and architecture duplication or rewriting of product-owner facts belong to L2 semantic checks. `ssot-lint.sh` only checks deterministic structure: STATUS required fields, required area rows, required product-skeleton shape, links, adapter shape etc.; whether body text can build a mental model, whether the entry holds independent facts, whether external diagrams are mistaken for authoritative diagrams, whether decomposition is mere directory mirroring, whether root/view lack domain evidence, whether product facts are duplicated in architecture, whether long-lived facts have a unique owner -- still Doctor-reviewer judgement.

## 3. Coverage hard blockers

When Doctor hits any of the following, the related product, architecture, testing, or other affected area cannot be marked `covered`. This blocks only SSOT coverage state, not daily code development.

- `architecture/README.md` is missing, or that file cannot build a quick mental model nor route to authoritative views/domains.
- After a new bootstrap or reorganization, the architecture root lacks design brief, system principles / operating model, primary journeys, core invariants, view index, Domain index, Current / Target / Gap summary, `decomposition_basis`, coverage or overview diagrams.
- The root, view or domain consists mainly of tables and lacks natural-language design-intent, constraints and trade-off narrative.
- A user-facing SSOT owner violates KISS: the main explanation lives in tables, duplicated sections restate the same fact, or the reader cannot tell the system story without reading row-by-row ledgers.
- A user-facing SSOT body file (`product/`, `architecture/` root/views/domains, `development/`, `testing/`, `benchmark/`, `release/`, deployment, `decisions/`, `gotchas/`, `bugs/`, `tech-debt/`, `glossary/`, root `SSOT/README.md`) violates prose-before-tables, positive-definition-on-first-use, or cell-is-not-a-paragraph (3+ cross-references / nested clauses / inline `BUG-`/`DEC-`/`ADJ-` reference plus a full verb clause). See [`ssot-bootstrap`](../../ssot-bootstrap/references/bootstrap.md) §3.7.
- `testing/` is used as a chronological verification ledger instead of a stable owner for test strategy, selection matrix, gates, fixtures, current baseline, known gaps, and defensive-test mapping.
- `testing/` hides benchmark suites, canonical workloads, measured metrics, floors, comparison rules, or trend interpretation that should live in `benchmark/`.
- `benchmark/` is missing when benchmark evidence guides engineering decisions, or `benchmark/` is used as a chronological run log instead of a stable owner for suites, workloads, metrics, environments, floors, comparison rules, trend interpretation, gaps, and decision links.
- The `Notes/备注` cells in `STATUS.md` are used as a child-entry status, latest validation, run-history, or proof-of-work ledger instead of project-level coverage pointers. Explicit Date columns are valid register fields and are not Notes.
- README/index/Reader Map files mirror child body facts, generated counts, latest activity, verification rows, or lifecycle state that belongs to entries/frontmatter/CI/release/bug owners.
- A non-authorized SSOT surface maintains a chronological shadow ledger; the affected area cannot be considered covered until the owner is restored or the ledger is explicitly authorized by protocol.
- A user-facing SSOT owner is present but not actionable: it lacks read trigger, current owner truth, first inspection points, do-not-do boundary, or minimal verification/evidence. For high-risk bug/debt entries, missing quick entry blocks claiming the affected bug/debt area as covered.
- `STATUS.md` stop-review fields contain full batch transcripts or command ledgers instead of concise conclusions and pointers to authorized evidence.
- Very long Markdown lines hide paragraph content inside a table cell or compressed note and make the owner hard to review.
- (v2.60) `STATUS.md` contains a data cell that exceeds its register-specific cap or embeds commands, checklists, multi-event chronology, or four-plus semicolon clauses (`[STATUS-REGISTER-CELL]`).

## 5. Pass / No-op review

If Doctor finds no issue, it still needs a scoped stop-review record before writing `passed` or `no-op`. The default is a scoped self-review recorded as `reviewer_role: scoped-self-review`. Use an independent reviewer only for bootstrap overall `passed`, a `documentation_language` change, a `semantic_impact=high` protocol upgrade, or the first declaration of `coverage_result=converged`.

The reviewer should read:

- `STATUS.md` and the stop-review gate.
- Doctor output.
- Sampled SSOT areas, especially `covered` areas.
- Related code/config/schema/test, source material, or diff/transcript evidence.
- Protocol upgrade notes corresponding to `tracked_skill_version`.

The reviewer returns:

- `no-more-required-changes`: may record Doctor pass or no-op in the `STATUS.md` stop-review gate.
- `needs-fix`: must list remaining changes; after fixing, re-run Doctor and the applicable stop review.

Without the applicable scoped stop review, Doctor results are check output only. A scoped self-review can support ordinary `passed`, `no-op`, `covered`, and tracking-baseline advancement; the four exceptions above require an independent signature.

## 6. Boundary with other flows

- **Commit audit**: catches up `tracked_commit..HEAD` code changes; see [`commit-audit.md`](../../ssot-audit/references/commit-audit.md).
- **Session audit**: catches up old transcripts after `tracked_session`; see [`conversation-audit.md`](../../ssot-audit/references/conversation-audit.md).
- **Protocol upgrade review**: catches `tracked_skill_version` up to the current `ssot-preflight` `metadata.protocol_version`; see [`protocol-upgrades.md`](../../ssot-audit/references/protocol-upgrades.md).
- **Knowledge integrity protocol**: full rules of the confidence state machine; see [`knowledge-integrity.md`](../../ssot-preflight/references/knowledge-integrity.md).
- **Thin-adapter protocol**: adapter content spec and generation rules; see [`adapter-strategy.md`](adapter-strategy.md).
- **Consumption audit**: evaluates the trigger/usage effectiveness of SSOT in real conversations (L4 behavioural probe), reverse-optimizing the trigger side; see [`consumption-audit.md`](consumption-audit.md). Doctor verifies content trustworthiness, consumption audit verifies trigger effectiveness; the two are orthogonal.
- **Doctor**: verifies trustworthiness of existing SSOT content; does not proactively interpret new diffs or new transcripts.

Proactive catch-up may combine these flows in any order, but every stop conclusion and tracking-baseline advance needs an explicitly scoped stop review. Independent review applies only to the four exceptions in `status-protocol.md` §6.
