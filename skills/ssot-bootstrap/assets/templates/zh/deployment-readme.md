当一个构建版本要进入他人或其它系统依赖的环境时，使用本页。执行前先决定目标
环境、准确产物或版本、预期可见结果、回滚所有者，以及哪个信号会停止上线。
安全动作是沿一条规范路径推进，在真实使用位置验证结果，然后完成交接，
或恢复到已知状态。

一个典型场景是服务升级：操作者确认目标和权限，部署一个已固定摘要的镜像，检查
就绪状态和代表性用户路径，再记录实际运行版本。就绪检查或用户路径失败时，
停止扩大范围，进入已记录的回滚或恢复分支。

## 部署开始前

部署者和批准者必须知道改什么、为什么现在改、谁有权修改目标，以及哪些环境和
数据在范围内。输入包括已固定版本的产物、配置来源、秘密访问权限、迁移状态、
当前健康状态和恢复目的地。权限缺失、产物未固定版本或回滚路径未知，都是停止条件。

## 规范路径

1. 确认目标、产物身份、当前状态、所有者和变更窗口。
2. 检查前置条件，并在写入前完成所需备份、快照、流量排空或批准。
3. 用仓库规定的部署命令或工作流，从最小安全范围开始。
4. 观察上线过程；命中健康、迁移、容量或用户路径失败信号时停止。
5. 在真实目的地验证部署版本、就绪状态、代表性行为和状态转换。
6. 扩大范围、完成交接，或执行回滚/恢复。长期结果写回其所有者；原始运行输出
   留在运行或交付产物中。

## 副作用与不可逆边界

部署可能替换进程、修改基础设施、迁移数据、清缓存、轮换凭据、通知外部系统、
消耗付费容量或中断用户。说明哪些可逆、哪些需要备份或补偿动作、哪些扩大后
无法撤销。不可逆步骤缺所有者、备份或验收信号时，必须先停下。

## 可观察结果与验收

命令成功只表示尝试过。验收意味着预期产物确实出现在预期目标，健康/就绪检查
有意义，代表性用户或操作者路径可用，状态或迁移检查符合预期。写明准确
观察点和验收人。

|---|---|---|---|
| | | | |

## 失败发现与停止条件

说明上线失败、实例不健康、数据结构不兼容、局部扩展、数据损坏、容量耗尽或
版本静默不一致的最早可信信号。指出哪个信号暂停上线、哪个强制回滚、哪个
必须升级处理而不是反复重试。

## 重试、回滚与恢复

只有确认失败步骤是否幂等、局部副作用是否仍在后才重试。回滚恢复上一可部署
状态；恢复也可能需要向前修复、恢复数据、隔离流量或生成新产物。说明怎样证明
恢复完成，并避免覆盖诊断所需证据。

## 升级与交接

按实际情况写出部署所有者、环境或基础设施所有者、数据所有者、安全批准者，
以及产品或发布接收者。交接包含目标、产物身份、观察状态、未解决风险和
下一项决定，而不只是日志链接。
