当一个已确认故障需要跨会话继续处理、像仓库以前修过的问题，或修好后再次出现
时，使用本索引。先匹配可观察特征，打开条目，只做安全复现，再跟随其中当前的
止损办法、下一步或回归检查，决定要委托什么；不要在证据成立前就认定它与历史
问题相同。

例如，页面在重连后变空，看起来像旧渲染缺陷。匹配条目应说明什么触发条件和
根因才算同一问题、当时怎样修、哪个测试能区分“复发”和新的失败方式。

这里保存长期故障知识，不代替事项跟踪系统。触发条件、时间线、生命周期理由、
事实与分析、证据是否仍有效、影响、根因、备选、修复、验证、所有者、预防以及复发或
关闭都由条目拥有；索引只路由。

## 缺陷索引

没有缺陷条目时，删掉示例行并显示下面这一行；出现真实条目后立即删掉本行：

空集合说明：原因=<具体理由>；负责人=[责任所有者](<可解析路径>)；复核条件=<可观察事件>。

每个真实条目必须且只能出现一行。编号与条目开头的 `id` 相同；“条目所有者”
链接必须能打开该文件；两个状态都与条目开头一致。`record_status` 说明这份知识
是否仍是当前路由材料；`failure_state` 说明这是尚未可靠修复的新问题、已经修好的
问题，还是修好后再次发生的问题。

路由状态只允许 `open`（尚未修复）、`fixed`（已修复）和 `recurred`（修复后再次
发生）。`open` 表示问题已经确认，但还没有经过合适验证的修复；`fixed` 表示条目
已有根因修复和合适回归证据；`recurred` 表示后续证据在一次修复后重新打开同一
失败方式，条目会解释为什么仍未解决。

兼容字段 `status` 可以继续存在，但必须镜像 `failure_state`，不能拿它表示
`record_status`。

## 创建或更新条目

每个值得长期保留的缺陷都要有完整条目，包括已经确认但修复尚未完成的新问题。
严重、重大和再次发生的缺陷必须按根因拆分，不能只写宽泛症状。没有可复用故障
经验的轻微修复可以不进入记录；一旦进入索引，也必须链接唯一条目所有者，不能
把根因故事藏进表格。

条目存在后再添加索引行。新确认且尚未解决的问题从 `open` 开始。复发时先更新
条目时间线和理由，再在这里镜像 `recurred`；合适证据关闭这两种状态时，先更新
条目，再镜像 `fixed`。

## 边界，以及何时重新检查

排期和分派仍属于事项跟踪系统。值得长期保留的已知未修复问题在这里保持 `open`。
被明确接受的临时绕过或设计折中可以另外形成[技术债](../tech-debt/README.md)，
但技术债不能代替缺陷本身的失败状态。没有缺陷生命周期的可重复陷阱属于
[陷阱](../gotchas/README.md)。触发路径、运行时、修复、测试、所有者或证据来源
变化时复核条目。
