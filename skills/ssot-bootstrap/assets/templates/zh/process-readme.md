当你已经确定仓库需要发生变化、但还没有选择命令或流程时，从这里开始。先判断
你需要哪类结果：修改代码、证明正确、比较可测量表现、操作运行环境、评估安全
或合规、把产物部署到环境，还是发布一个版本。随后只打开拥有这类工作的子页面，
按其中的当前路径执行。

例如，修改一个 API 通常先读[开发](./development/README.md)，再按
[测试](./testing/README.md)选择检查；只有环境也要变化时，才继续到
[部署](./deployment/README.md)。本页解释这条路线，不复制这些所有者的命令或
验收规则。

## 选择下一位所有者

- 需要配置仓库、修改代码或遵循工程约定时，读[开发](./development/README.md)。
- 需要判断该跑哪些正确性检查、什么会阻塞验收时，读
  [测试](./testing/README.md)。
- 决定依赖延迟、吞吐、容量、成本或其它可比较工作负载时，读
  [基准测试](./benchmark/README.md)。
- 产物要进入环境，需要分批上线、验证、回滚或运维动作时，读
  [部署](./deployment/README.md)。
- 要生成并保持版本、包、标签、变更日志或公开交付一致时，读
  [发布](./release/README.md)。
- 处理线上运维或安全/合规工作时，先读 [区域状态](../STATUS.md#区域状态) 中的
  对应行。这两类所有者只在适用时建立：目录存在就跟随该行的所有者；确实不适用
  就跟随有理由的边界说明。目录缺失本身是缺口，不等于这类工作没有必要。

一项任务跨多个所有者时，把顺序写清楚。不要把“测试通过”误认为已经部署，
不要用基准测试代替正确性检查，也不要假设部署自然等于发布。

## 路由表

理解上面的路线后，再用此表快速跳转。每个链接页面仍是详细事实的唯一所有者。

| 读者要做的决定 | 第一站 | 何时继续 |
|---|---|---|
| 怎样安全完成这次改动？ | [开发](./development/README.md) | 改动已准备好接受所需检查。 |
| 什么证据能证明改动正确？ | [测试](./testing/README.md) | 还需要稳定的性能或成本比较。 |
| 哪个测量结果可以比较？ | [基准测试](./benchmark/README.md) | 结果会改变决定、闸门或已知缺口。 |
| 这个版本怎样进入环境？ | [部署](./deployment/README.md) | 部署结果已验证或已回滚。 |
| 版本怎样发布和通知？ | [发布](./release/README.md) | 发布产物与目的地一致。 |
| 怎样观察、缓解并恢复运行环境？ | [区域状态中的 operations 行](../STATUS.md#区域状态) | 跟随条件所有者或有理由的边界。 |
| 需要什么安全、隐私或合规证明？ | [区域状态中的 security 行](../STATUS.md#区域状态) | 跟随条件所有者或有理由的边界。 |

任务触及 Q01-Q21 时，从 [STATUS 的质量、风险与治理登记表](../STATUS.md#质量风险与治理)
开始。那里分别指向唯一产品承诺、架构执行、流程/证据所有者和未解决缺口；
本路由不复制这些事实。

## 边界与交接

本目录拥有可重复的工程流程。产品承诺属于[产品](../01-product/README.md)，
运行时设计属于[架构](../02-architecture/README.md)，事故知识和仍开放的具名工作
属于[记录](../04-records/README.md)。子流程可以链接这些所有者，但不能改写
它们的事实。

路线缺失或互相矛盾时，在不可逆步骤前停止。写明不确定点、所有者和证据方向，
再把问题交给其输出或恢复决定被阻塞的子流程。

## 何时复核

新增、删除、改名流程目录，或目录职责变化时，复核本路由。命令、权限、环境、
闸门、回滚或验收规则变化时，更新对应子页面，不在本页复制一份；Q01-Q21 的
所有者路由变化时，再复核本页。
